### 3.2 架构形态与分层

采用 Nuxt 全栈同仓架构：

1. **app 目录**承载页面、组件、状态与前端业务逻辑
2. **server/api 目录**承载 BFF/Mock 接口
3. **composables** 统一封装 API 契约与状态访问

分层设计：

| 层           | 职责                                   |
| ------------ | -------------------------------------- |
| 展示层       | pages + components                     |
| 状态层       | Pinia Store（useState/useCookie 辅助） |
| 数据访问层   | useApi 统一请求客户端                  |
| 服务层       | server/api 各业务 handler              |
| 外部能力层   | SiliconFlow、远端角色数据服务          |

### 3.3 渲染模式

| 页面       | 渲染方式     | 说明                                     |
| ---------- | ------------ | ---------------------------------------- |
| 首页       | SSR          | SEO 友好，服务端直出                     |
| 商品商店   | SSR          | SEO 友好，首屏数据预取                   |
| 商品详情   | SSR          | SEO 友好                                 |
| 博客       | SSR          | SEO 友好，内容可被爬虫抓取               |
| AI 对话    | CSR Only     | `.client.vue` 跳过 SSR，避免 AI SDK 报错 |
| 角色展示   | SSR + CSR    | 数据预取 + 客户端动画                    |
| 关于我     | SSR + CSR    | 静态内容 SSR + GSAP 动画客户端           |

## 5. 状态管理架构

### 5.1 Store 总览

项目使用 **Pinia 3** 进行状态管理，采用 Composition API 风格（`setup` 函数）。全局状态优先 `useState`，鉴权状态使用 `useAuthState` + `auth_token` Cookie，主题状态使用 `useThemeMode` + localStorage 持久化。

#### Auth Store（`stores/auth.ts`）

```typescript
// 状态
token: string | null           // JWT Access Token
refreshToken: string | null    // JWT Refresh Token
user: AuthUser | null          // { id, username }

// 计算属性
isAuthenticated: boolean       // token 或 refreshToken 存在即为 true

// 方法
initAuthFromCookie()           // 从 Cookie 恢复认证状态
setAuth({ token, refreshToken, user })  // 设置认证（内存 + Cookie 双写）
clearAuth()                    // 清除认证（内存 + Cookie 双清除）
```

**Cookie 策略**：
- `auth_token`：存储 Access Token
- `refresh_token`：存储 Refresh Token
- 仅在客户端（`import.meta.client`）操作 Cookie

#### Theme Store（`stores/theme.ts`）

```typescript
// 状态
mode: 'system' | 'light' | 'dark'   // 主题模式

// 方法
setMode(value)                        // 设置主题模式
```

#### UI Store（`stores/ui.ts`）

```typescript
// 状态
authModalOpen: boolean              // 认证弹窗是否打开
authModalView: 'login' | 'register' // 当前视图

// 方法
openAuthModal(view)                 // 打开弹窗（指定登录/注册视图）
closeAuthModal()                    // 关闭弹窗
```

### 5.2 数据流

```
用户操作 → UI Store (弹窗控制)
         → Auth Store (登录/注销)
         → API 层 (useApi)
         → 后端服务
         → 响应数据 → Store 更新 → 视图响应式更新
```

## 6. API 层封装设计

### 6.1 核心客户端（`composables/useApi.ts`）

`useApi` 是全局唯一的 HTTP 客户端工厂，基于 Nuxt 内置的 `$fetch` 封装。

#### 核心特性

| 特性               | 实现方式                                           |
| ------------------ | -------------------------------------------------- |
| **统一 BFF 前缀**  | 浏览器侧所有请求统一走 `/api/v1`（Nuxt server/api 的 BFF 路由），由 BFF 层再转发后端（详见 6.5） |
| **Bearer Token**   | `onRequest` 拦截器自动附加 Authorization 头        |
| **401 静默刷新**   | 自动使用 refresh_token 刷新，刷新期间挂起其他 401 请求（全局 refreshPromise 锁） |
| **请求去重**       | 基于 `Method+URL+Params+Body` 指纹的 Promise Lock  |
| **错误 Toast**     | 客户端自动弹出 Nuxt UI Toast，2 秒防抖，401 不弹   |
| **网络错误识别**   | 区分网络层错误（友好提示，不暴露内部 URL）与业务层错误（展示服务端消息） |
| **关闭默认重试**   | `retry: 0`，重试与降级由 BFF 层统一处理            |
| **凭证携带**       | `credentials: 'include'`                           |

#### 请求流程

```
发起请求 → 生成请求指纹
    ↓
[命中锁?] → 是 → 复用已有 Promise
    ↓ 否
附加 Bearer Token → 发送请求
    ↓
[响应 code === 200?] → 是 → 返回 data
    ↓ 否
[状态码 401?] → 否 → handleError (Toast 提示)
    ↓ 是
[已有刷新任务?] → 是 → 等待刷新结果
    ↓ 否
发起 refresh_token 请求
    ↓
[刷新成功?] → 是 → 重试原请求
    ↓ 否
清除认证 → 弹出登录弹窗
```

#### 对外接口

```typescript
const { get, post, put, del } = useApi()

get<T>(url, params?, options?)    // GET 请求
post<T>(url, body?, options?)     // POST 请求
put<T>(url, body?, options?)      // PUT 请求
del<T>(url, options?)             // DELETE 请求
```

### 6.5 BFF 层设计（`server/utils/bff.ts`）

前端不直连后端 Flask，而是经由 Nuxt 服务端的 BFF（Backend For Frontend）层转发。该层是本项目前后端解耦的核心边界。

#### 6.5.1 分层与两条路径

```
浏览器 ──(/api/v1/*)──▶ Nuxt BFF ──(NUXT_API_SECRET_BASE)──▶ Flask
         ↑ 同源、公开         ↑ 契约适配/降级/鉴权    ↑ 内网/服务端专属
```

| 层次 | 路径 | 使用方 | 说明 |
| ---- | ---- | ------ | ---- |
| BFF 暴露层 | `/api/v1/*` | 浏览器（`useApi` 的 `baseURL`） | Nuxt server/api 路由，同源、公开 |
| 后端转发层 | `NUXT_API_SECRET_BASE`（本地 `:5050/api/v1`，线上 `/uapi`） | 仅服务端 | 由 Nginx 的 `/uapi` location 转发至 Flask |

> ⚠️ **常见误区**：`/api/v1` 与 `/uapi` 不是同一层。前者是前端调 Nuxt 的地址，后者是 Nuxt 调 Flask 的地址。前端请求 `/uapi` 会绕开 BFF，丢失 Mock 降级、Token 注入、字段归一化等全部能力。

#### 6.5.2 核心方法

| 方法 | 行为 | 适用场景 |
| ---- | ---- | -------- |
| `proxyToBackend` | 单纯转发到 Flask，失败抛错 | 内部复用 |
| `withMockFallback` | 优先代理，**失败降级 Mock** | 可容忍假数据的读接口（商品/首页/文章） |
| `proxyOnly` | 纯代理，**失败直接抛错** | 登录、支付等写操作，禁止伪造结果 |
| `withMockOrProxy` | 仅 Mock 模式下返回 Mock，否则纯代理 | 兼容无后端联调、又不允许故障期降级 |

**降级策略**（`withMockFallback`）：

1. `NUXT_PUBLIC_USE_MOCK=true` → 直接返回 Mock
2. 代理成功 → 响应头 `X-Data-Source: backend`
3. 代理失败 → 降级 Mock，响应头 `X-Data-Source: mock`
4. 例外：`401 / 403 / 422` 属业务语义，**原样透传**，不用 Mock 掩盖

> `X-Data-Source` 响应头是判断"数据来自后端还是 Mock"的最快依据。

#### 6.5.3 BFF 的职责（为什么需要它）

1. **字段契约适配**：Flask 的 `home/data` 返回 snake_case（`sale_price`/`image`）且不下发 `code`，搜索系列返回 camelCase（`salePrice`/`main_image`）。由 `normalizeProduct` / `normalizeProductList`（`server/utils/product.ts`）在 BFF 层统一收敛为前端 `Product` 契约，并补全缺失的 `code`（`prd_{id}`）。
2. **Mock 降级容错**：降级发生在服务端，浏览器无感；后端故障时前端不会白屏。
3. **凭证与后端地址隔离**：`apiSecretBase` 位于 `runtimeConfig` 顶层（非 `public`），浏览器 JS 无法获取 Flask 真实地址，也无法绕过 BFF。
4. **鉴权转发**：`buildForwardHeaders` 统一注入 `Authorization` 与 `X-Forwarded-For`；登录/支付等接口用 `proxyOnly` 保证绝不签发假凭证。
5. **统一响应与错误语义**：出入参统一为 `{ code, message, data }`，前端仅按 `code === 200` 判定成功。
6. **SSR 数据获取与缓存**：SSR 阶段服务端内网直连 Flask，无跨域；首页聚合接口通过 `routeRules` 配 60s SWR 缓存。

#### 6.5.4 运维要点（踩坑记录）

1. **Nginx 路由必须区分前缀**：`/api/` 若被重写转发给 Flask（管理端 `/system/` 规则），会抢占 Nuxt 的 BFF 路由，导致浏览器请求 404。需为 `/api/v1/` 单独配置更长前缀的 location 指向 Nuxt（3000）。
2. **容器必须注入后端地址**：部署时 `NUXT_API_SECRET_BASE` 未注入会回退默认值 `http://127.0.0.1:5050/api/v1`（容器内指向自身），导致 BFF 静默降级为 Mock。Nuxt runtimeConfig 支持通过 `NUXT_` 前缀环境变量在运行时覆盖，无需重新构建。
