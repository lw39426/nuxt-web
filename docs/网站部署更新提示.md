# 网站部署更新提示

## 选型对比

| 方案 | 所需配合 | 优点 | 成本与限制 |
| --- | --- | --- | --- |
| Nuxt 原生 App Manifest 检测 | Nuxt 和静态资源缓存配置 | 自动生成构建 ID、版本文件和轮询逻辑，随构建产物发布 | 受 Nuxt 检测行为及浏览器后台定时器限制 |
| 自建 version.json 与轮询 | 构建脚本、前端检测代码 | 可自由配置立即检查、页面恢复检查、重试和延后提醒 | 需要维护版本生成、一致性和请求生命周期 |
| SSE / WebSocket | 推送服务、部署通知、前端连接 | 通知及时 | 需要处理连接、重连、多实例广播 |
| Service Worker | PWA 注册及缓存策略 | 能配合离线资源更新 | 引入额外缓存生命周期，当前项目无此需求 |

## 选择原因

项目安装 Nuxt 4.6.2，已经具备 App Manifest 和 `app:manifest:update` 钩子。采用原生机制能让版本 ID、清单和客户端代码由同一次构建生成，避免重复维护版本文件。刷新提示使用已有 Nuxt UI 按钮，支持现有主题。

本次选择每两分钟检测和常驻提示。用户自行保存内容后点击刷新。提示不自动消失，用户可以继续使用页面。Flask 无需增加接口。

## 当前构建与部署

以下结论来自仓库配置，未登录生产服务器核实。

- `package.json` 使用 pnpm 10.14.0，`pnpm run build` 执行 `nuxt build`，输出 `.output`。另有 `generate` 静态生成命令。
- `.github/workflows/deploy.yml` 在 main 推送或手动触发时运行。使用 Node 22，依次安装依赖、Lint、格式检查、测试、构建，然后通过 SSH 上传 `.output`。
- 服务器将产物放入 `/data/www/nuxt-web/releases/<时间戳>`，切换 `current` 软链。实际工作流使用 `pm2 delete` 加 `pm2 start`，存在短暂服务中断，配置文件注释中的 reload 描述与实际流程不同。
- PM2 以 cluster 模式运行 Nitro，监听 `127.0.0.1:3000`。BFF 访问同机 Flask。
- 部署通过首页 API 的 `X-Data-Source: backend` 响应头判断健康，失败回滚，成功后保留最近五个版本。
- Dockerfile 是另一种运行入口，复制已有 `.output` 并启动 Node，当前部署工作流未使用 Docker。
- 仓库未提供生产 Nginx/CDN 配置，因此无法确认线上缓存规则。

## 实现过程

### 1. 启用原生构建清单检查

`nuxt.config.ts` 显式设置 `experimental.appManifest: true` 和 `experimental.checkOutdatedBuildInterval: 120000`。

Nuxt 构建生成 `/_nuxt/builds/latest.json` 以及 `/_nuxt/builds/meta/<buildId>.json`。浏览器比较当前构建清单与线上最新清单的 ID，变化后触发 `app:manifest:update`。回滚的 ID 同样会不同。

当前 Nuxt 实现会在应用就绪约两分钟后首次检查，之后继续轮询，检测到更新后停止轮询。请求最新清单时附带时间戳。后台标签页可能被浏览器延迟执行，当前实现没有额外增加切回标签页立即检查。

### 2. 添加全局提示组件

`app/components/AppUpdateNotice.vue` 订阅更新钩子，收到事件后展示常驻提示，卸载时移除订阅。组件使用 Composition API 和 TypeScript，提示带有 `role="status"`，适配深浅主题与移动端宽度。

`app/app.vue` 在现有 `ClientOnly` 中挂载组件，使其跨路由持续存在。点击按钮调用 `window.location.reload()`，保留当前地址的路径、查询参数及 hash。

页面提示保存内容，未添加统一的表单脏状态检测或草稿保存。浏览器刷新会丢弃未持久化的输入，Vue 路由离开守卫不会拦截整页刷新。

### 3. 缓存与上线

为 `/_nuxt/builds/latest.json` 配置 `Cache-Control: no-store`。如果 Nginx 直接提供静态文件，或 CDN 覆盖上游响应头，需要在相应层为该路径配置不缓存。HTML 也应及时重新验证，带哈希的 JS/CSS 可以长缓存。

清单随现有 `.output` 上传，无需独立版本生成脚本。版本变化表示访问到另一个构建，并不表示 CI 健康检查已完成。当前软链切换发生在健康检查之前，失败并回滚时可能短暂出现提示。

保留 releases 目录不等于旧哈希资源仍可经线上 URL 访问。旧页面按需加载旧 JS 是否成功，取决于服务器静态资源保留策略，需要上线时核实。

首次上线此功能之前已经打开的旧页面没有提示代码，需要先刷新加载本次版本，后续发布才会收到提醒。

## 验收步骤

1. 构建并运行版本 A，打开页面并保持标签页。
2. 重新构建版本 B，按相同入口切换产物。等待约两分钟，确认 A 页面显示一次提示。
3. 点击刷新更新，确认地址保留、加载 B 后提示消失。
4. 保持 B 页面并回滚至 A，确认能再次提示。
5. 检查线上 `/_nuxt/builds/latest.json` 的 ID 与发布产物一致，响应头不缓存。确认没有 CDN 的旧响应命中。
6. 检查移动端、深浅主题、键盘按钮操作，以及发布短暂中断后检测是否恢复。

Nuxt 内置检测对最新清单请求失败会忽略并继续轮询。当前构建清单读取发生其他错误时存在框架自身的重试限制，应通过网络面板排查，而不能把没有提示直接认定为没有更新。

## 本次验证结果

生产构建通过，确认产物生成最新构建清单。既有 77 项测试及新增提示组件测试通过，改动文件 ESLint 和格式检查通过。组件测试覆盖初始隐藏、重复事件只展示一次、点击刷新与卸载清理。当前环境未配置 Chrome DevTools MCP，未完成真实浏览器视觉检查及线上双版本切换验收。
