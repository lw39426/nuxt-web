# 时间格式与前端展示约定

适用：管理端与用户端的时间戳字段。本文说明当前 UTC 接口契约；纯日期（生日、统计日期）和过期秒数不适用。

> 部署核验前提：`Z` 是接口声明的 UTC 时区，不能据此证明库内值确实为 UTC。如果北京时间 16:30 操作，返回却为当天 `16:30:01Z`，需优先排查本地时间被当作 UTC 的写入问题。正确 UTC 应为当天 `08:30:01Z`。在此问题查清前，前端不要通过删除 `Z` 或统一减 8 小时补偿。

## 接口与显示

- 响应统一使用 ISO 8601 UTC 字符串，精确到秒：`YYYY-MM-DDTHH:mm:ssZ`；可空字段返回 `null`。
- `Z` 表示 UTC。`2026-10-29T16:30:01Z` 对应北京时间 `2026-10-30 00:30:01`，跨日正常。
- 前端提交时间建议使用 `Z` 或明确偏移，例如 `2026-10-30T00:30:01+08:00`。后端解析后存储为无时区的 UTC datetime。
- 兼容输入 `2026-10-30 00:30:01` 和不带时区的 ISO 字符串时，后端将其视为 **UTC**，不会自动视为北京时间。日期选择器的本地值应先明确时区再提交。
- 不要删除 `Z`、用字符串截取代替时区转换，或在 Date 已转换后手动加 8 小时。URL 查询中的 `+08:00` 应通过 `URLSearchParams` 编码，防止 `+` 被解释为空格。

## 前端示例

```javascript
// 固定以北京时间展示，避免用户电脑时区影响管理列表。
export function formatBeijingTime(value) {
  if (!value) return '-';
  const date = new Date(value);
  if (Number.isNaN(date.getTime())) return '-';
  const parts = new Intl.DateTimeFormat('en-GB', {
    timeZone: 'Asia/Shanghai',
    year: 'numeric', month: '2-digit', day: '2-digit',
    hour: '2-digit', minute: '2-digit', second: '2-digit', hourCycle: 'h23',
  }).formatToParts(date);
  const p = Object.fromEntries(parts.map(({ type, value }) => [type, value]));
  return `${p.year}-${p.month}-${p.day} ${p.hour}:${p.minute}:${p.second}`;
}

formatBeijingTime('2026-10-29T16:30:01Z'); // 2026-10-30 00:30:01

// 北京时间选择器值；仅在该控件明确以北京时间输入时追加 +08:00。
const selected = '2026-10-30 00:30:01';
const start_time = new Date(selected.replace(' ', 'T') + '+08:00').toISOString();
// 2026-10-29T16:30:01.000Z（输入支持毫秒；响应统一到秒）
```

## Banner 与检查结果

`GET /system/banners`、`GET /system/banners/<id>` 及创建响应均调用 `Banner.to_dict()`，`start_time`、`end_time`、`created_at`、`updated_at` 全部使用 `format_utc_iso()`。创建、更新及列表 `effective_time` 输入使用 `parse_iso_to_naive_utc()`。

其他模型序列化也普遍使用 `format_utc_iso()`。本次扫描模型和视图中的直接 `strftime` / `isoformat` 调用，主要剩余项为生日、统计日期，以及后台登录会话的 `expires` 展示字符串；不能把这些字段机械地全部改成时间戳格式。

写入侧仍需关注（不能仅靠返回字符串判断历史数据是否正确）：

- Banner、公告、商品、地区角色、聊天等模型使用数据库 `func.now()`。应用数据库初始化现已为 MySQL/MariaDB 的每个新物理连接设置 `SET SESSION time_zone = '+00:00'`，覆盖主库及 binds；SQLite 保持原有 UTC 行为。部署后须重启 Web 与所有后台 worker，使连接池重建。配置中的 `TIMEZONE=Asia/Shanghai` 不等于设置数据库会话时区。本次未连接生产数据库核验。
- 该设置影响新写入及后续更新时间，不会自动修正历史 DATETIME。数据库外部脚本或直接 SQL 写入也需自行遵守 UTC。若存在 TIMESTAMP 列，其读取会随会话时区转换，应在部署前核验实际表结构。
- `applications/models/backend/__init__.py` 部分默认值使用 `default=datetime.now(UTC)` / `onupdate=datetime.now(UTC)`，在模块加载时即求值，存在时间固定风险；需要单独改为 callable 并验证实际写入。
- 不应对历史数据统一减 8 小时；需先确定数据来源和数据库会话时区，避免重复转换。本文不执行历史数据修正或数据库迁移。
