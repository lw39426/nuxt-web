## 技术选型

| 工具 | 用途 | 理由 |
|---|---|---|
| **Vitest 3.2** | 测试运行器 | Nuxt 官方推荐，Vite 原生，单一 runner 覆盖单元+组件 |
| **@vitejs/plugin-vue 6** | 编译 `.vue` SFC | Vitest 内解析 Vue 组件必需 |
| **@vue/test-utils 2.4** | 组件挂载 | 用 `mount` + global stubs，避免 `@nuxt/test-utils` 的 Nuxt 4 兼容风险 |
| **happy-dom 15** | 组件测试 DOM 环境 | 比 jsdom 快，逻辑/emit 测试足够 |
| **@vitest/coverage-v8** | 覆盖率 | v8 provider |

**关键决策：不引入 `@nuxt/test-utils`。** 用 `@vue/test-utils` + `#imports` alias stub 替代 `mountSuspended`，避免 Nuxt 4 兼容性风险、零 Nuxt 启动开销。

## 架构设计

### 核心问题：Nuxt 自动导入在 Vitest 中不可用

Nuxt 把 `useRuntimeConfig`、`useCookie`、`useToast`、`ref`（部分场景）等编译到虚拟模块 `#imports`。Vitest 不运行 Nuxt 编译流程，导致这些导入无法解析。

**解决方案：`resolve.alias` 重定向 `#imports`。**

```ts
// vitest.config.ts
export default defineConfig({
  resolve: {
    alias: {
      '~': fileURLToPath(new URL('./app', import.meta.url)),
      '#imports': fileURLToPath(new URL('./tests/test-utils/nuxt-imports-stub.ts', import.meta.url)),
    },
  },
})
```

这样任何 `.ts` / `.vue` 文件里的 `import { useCookie } from '#imports'` 都会解析到我们的 stub 文件。

### stub 文件：`tests/test-utils/nuxt-imports-stub.ts`

这是所有 Nuxt 自动导入的**唯一假实现源**：

```ts
import { vi } from 'vitest'
import { ref, computed, type Ref } from 'vue'

// cookieStore 通过 globalThis 单例共享（避免模块复制问题）
export const cookieStore = new Proxy(new Map(), { /* 转发到 globalThis 单例 */ })

export const useRuntimeConfig = vi.fn(() => ({ /* ... */ }))
export const useCookie = vi.fn((key) => { /* 从 globalThis Map 读取/创建 ref */ })
export const useToast = vi.fn(() => ({ add: toastAdd }))
export const toastAdd = vi.fn()
// ... 更多 mock 函数

export function resetNuxtImportsStub() {
  // 在每个测试的 beforeEach 调用
}
```

**为什么用 `globalThis` 单例而不是裸 Map？** `vi.mock('#imports')` 的工厂在 Vitest 的 mock 注册表中可能被复制一份模块作用域，导致工厂闭包里的 Map 与测试文件 import 到的 Map 不是同一个实例。`globalThis` 上的引用不受模块复制影响。

### `import.meta.client` 注入

```ts
// vitest.config.ts（顶层，不是 test.define）
export default defineConfig({
  define: {
    'import.meta.client': 'true',   // 让 store/useApi 进入客户端分支
    'import.meta.server': 'false',
  },
})
```

**注意：** 必须放在 `defineConfig` 的顶层，不能放在 `test.define` 里——Vitest 3 的 `test.define` 无法注入 `import.meta.*`。

### 测试隔离策略

#### 纯函数 / SDK 测试（无状态泄漏）

直接 `import` 被测模块即可，天然隔离。

#### Pinia Store 测试

```ts
import { createPinia, setActivePinia } from 'pinia'
import { useAuthStore } from '~/stores/auth'

beforeEach(() => {
  setActivePinia(createPinia())  // 每个测试全新 Pinia 实例
  cookieStore.clear()
})
```

**注意：** Pinia setup store 会自动解包 ref，访问 `store.token` 而非 `store.token.value`。

#### 组件测试

```ts
// @vitest-environment happy-dom（文件顶部指令切换环境）
import { mount } from '@vue/test-utils'
import { vi } from 'vitest'

// 组件里裸用的 Nuxt 自动导入（如 navigateTo）通过 globalThis 注入
const navigateTo = vi.fn()
vi.stubGlobal('navigateTo', navigateTo)

const wrapper = mount(Component, {
  props: { ... },
  global: {
    stubs: { 'el-card': { template: '<div><slot /></div>' } },  // stub 子组件
  },
})
```

#### useApi 测试（最复杂）

useApi 模块内部持有模块级可变状态（`refreshPromise` / `requestLocks` / `errorToastCache`），跨测试会泄漏。

**解决方案：`vi.resetModules()` + 动态 import。**

```ts
async function freshApi() {
  vi.resetModules()                                  // 清空模块缓存
  const stub = await import('#imports')              // 重新导入 stub（拿到新 vi.fn 实例）
  const mod = await import('~/composables/useApi')   // 全新 useApi 模块实例
  api = mod.useApi()
  return { api, cookieStore: stub.cookieStore, useCookie: stub.useCookie }
}

it('401 刷新', async () => {
  cookieStore.set('refresh_token', ref('rt_valid'))   // 先 seed cookie
  await freshApi()                                    // 再创建 api（让 useCookie 捕获带值的 ref）
  // ... 配置 mockClient / $fetch，发起请求
})
```

**关键细节：**
- `resetModules()` 后 stub 模块也被重置（`vi.fn` 换成新实例），所以必须重新 `import('#imports')`
- cookie 必须在 `freshApi()` 之前 seed，因为 `useApi()` 内部调用 `useCookie()` 会捕获当时的 ref
- 假 store 状态放在 `globalThis` 单例上，避免模块重置后状态丢失
- 错误 toast 测试使用**不重复的 code+message 键**，避开跨测试的 `errorToastCache` 累积

## 如何编写新测试

### 新增纯函数测试

直接在 `tests/unit/utils/` 下创建 `xxx.test.ts`，导入被测函数，写断言。无需特殊 setup。

### 新增 Store 测试

```ts
import { describe, it, expect, beforeEach } from 'vitest'
import { createPinia, setActivePinia } from 'pinia'
import { cookieStore } from 'tests/test-utils/nuxt-mocks'  // 或从 #imports 导入
import { useXxxStore } from '~/stores/xxx'

describe('useXxxStore', () => {
  beforeEach(() => {
    setActivePinia(createPinia())
    cookieStore.clear()
  })

  it('...', () => {
    const store = useXxxStore()
    // store.xxx 不是 store.xxx.value（Pinia setup store 自动解包）
  })
})
```

**如果 store 使用了 `useCookie` / `useRuntimeConfig` 等 Nuxt 自动导入：**
- 确保 store 文件有显式 `import { useCookie } from '#imports'`
- stub 会自动注入，无需额外 mock

### 新增 Composable 测试

- 如果 composable **没有模块级可变状态**：直接 import，正常测试
- 如果 composable **有模块级状态**（如 useApi）：参考 useApi 测试的 `freshApi()` 模式

### 新增组件测试

```ts
// @vitest-environment happy-dom
import { describe, it, expect, vi } from 'vitest'
import { mount } from '@vue/test-utils'
import XxxComponent from '~/components/XxxComponent.vue'

// 如果组件裸用 Nuxt 自动导入（如 navigateTo），注入 globalThis
const navigateTo = vi.fn()
vi.stubGlobal('navigateTo', navigateTo)

describe('XxxComponent', () => {
  it('renders', () => {
    const wrapper = mount(XxxComponent, {
      props: { ... },
      global: {
        stubs: { '子组件标签': { template: '<div><slot /></div>' } },
      },
    })
    expect(wrapper.text()).toContain('...')
  })
})
```

**注意：**
- 文件顶部必须有 `// @vitest-environment happy-dom`
- 在 `tests/components/` 目录下的测试默认用 happy-dom
- stub 子组件（el-card / el-button 等 UI 库组件），只测本组件逻辑
- UnoCSS 样式在测试中不处理，断言不涉及样式

## 常见问题

### Q: `useRuntimeConfig is not defined`

源文件缺少显式 import。在文件顶部添加：
```ts
import { useRuntimeConfig } from '#imports'
```

### Q: `ref is not defined` / `computed is not defined`

Nuxt 自动导入的 Vue 函数在 Vitest 中不可用。添加显式 import：
```ts
import { ref, computed } from 'vue'
```

### Q: `getActivePinia()` was called but there was no active Pinia

在 `beforeEach` 中调用 `setActivePinia(createPinia())`。

### Q: Pinia setup store 的 ref 需要 `.value` 吗？

**不需要。** Pinia setup store 自动解包 ref，`store.token` 直接拿到值。

### Q: 测试之间状态泄漏

- Store 测试：每个测试用 `setActivePinia(createPinia())` 创建新实例
- useApi 测试：用 `vi.resetModules()` + 动态 import
- 错误 toast 测试：使用唯一的 error key

### Q: `vi.mock('#imports')` 与 alias 冲突

不要同时使用。本项目用 alias 方案，不要在测试文件里 `vi.mock('#imports')`。

## CI 集成

`.github/workflows/test.yml` 在 PR / push 到 develop/feature 分支时自动运行：

```yaml
- name: Unit + Component tests
  run: pnpm run test
```

`vitest run` 在测试失败时退出非零，阻断后续的 Build test 步骤，满足"测试失败阻断合并"。

### 覆盖率阈值

当前阈值（`vitest.config.ts`）：

```ts
thresholds: { lines: 3, functions: 5, branches: 2, statements: 3 }
```

起步设低，后续随测试补充逐步调高。
